# ROZ-110 / ROZ-111 Breaker Round 5 Evidence

Date: 2026-08-28

Scope: parts/media, scanner, and stickers API/tests/screens plus the QR dependency manifest/lockfile. No shared route or registry edits, Git mutations, browser automation, E2E, or full-suite execution.

## Implemented behavior

- Parts create, edit, and delete evaluate the supplied module definition against the current cabinet tenant snapshot. `parts.manage` and subscription state fail closed for every mutation; the parts quota applies only to create.
- Parts page numbers accept every positive integer while `per_page` remains capped at 100.
- Vehicle and intake filters/source inputs use tenant-scoped labeled data from the immutable cars/intakes list endpoints and persist the selected IDs without displaying raw internal IDs. The lists are requested only when their selector is relevant and the cabinet snapshot grants the corresponding `cars.view` or `intakes.view` permission; unauthorized source choices are not offered on create. Failed list loading produces an explicit selection/search limitation.
- Parts create/edit provides an accessible multi-file image input backed by the confirmed `POST /media/upload?entityType=parts` contract. Each file has independent uploading, success, failure, retry, and removal state, so partial success is retained and save remains disabled until failed/in-flight work is retried or removed. Create/update send only committed `photoKeys`; new uploaded files are deleted through `DELETE /media` when removed before save. Existing photo URLs use opaque labels, allowed HTTP(S) URLs, and never render storage keys.
- Part detail/history renders notes, total/available/reserved/sold quantities, creator/time, source, related orders, and edit navigation. Vehicle, intake, order, edit, and delete controls are permission-aware.
- Aborted or stale parts list/detail requests cannot replace current data with an error.
- Scanner camera shutdown is centralized. Manual, file, and live success stop the stream; retry denial stops the previous stream; camera/file generations reject delayed results; unmount aborts an active lookup and ignores delayed file detection.
- Sticker queue selection uses a tenant-scoped labeled parts list and requires `stickers.manage` for generation preparation.
- `qrcode@1.5.4` with `@types/qrcode@1.5.6` generates real SVG QR markup. Every QR encodes the stable own-origin `/scan/:qrCode` resume URL with the code encoded as one path segment. The same SVG artifact is used for preview, printable HTML download, print, and Web Share file sharing when supported; temporary download object URLs are always revoked.

## Contract evidence and adjudicated blockers

- Authoritative OpenAPI: `POST /api/v1/media/upload` accepts multipart `file` and `entityType=parts`, returning required `MediaUploadResult.storageKey` and `.url`; `CreatePartRequest.photoKeys` is required and `UpdatePartRequest.photoKeys` is optional/nullable. The existing `src/api/media.ts` matches the upload and delete contracts.
- The prior QR blocker is resolved by the maintained browser-compatible encoder dependency. No backend PDF endpoint was invented: the supported artifact is printable HTML containing actual SVG QR codes.
- No unresolved blocker remains within this round's owned scope.
