# Розбіжності макетів і застосунку

Журнал переносу макетів Claude Design у кабінет. Для кожного екрана —
що з логіки макета застосунок уже вміє, а чого не вміє й чому.

Поповнюється по одному екрану, у порядку артефактів.

---

## 1. Додати деталь у приймання — `/intakes/:intakeId/parts/new`

Артефакт: `6344180d-ec27-454b-996a-19d0be38e57e`
Реалізовано: так, UI за макетом.

### Працює по-справжньому

| Елемент макета                                             | Як зроблено                                                                                     |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Назва, тип деталі, нотатки, фото                           | `POST /intakes/{id}/parts`                                                                      |
| Стан чипами (б/в · після ремонту · нова · під відновлення) | ті самі чипи, значення мапляться в серверний enum `good / refurbished / new / scrap`            |
| Кількість кнопками − / +                                   | новий примітив `QuantityStepper`, число й далі можна ввести з клавіатури                        |
| Комірка                                                    | `inventoryZoneIds` у тому ж запиті; список комірок — `GET /inventory/zones?activeOnly=true`     |
| Собівартість на одиницю                                    | рахується з приймання: `totalCost / partsCount`                                                 |
| Ціна продажу                                               | приймання її не приймає, тому одразу після створення йде `PUT /parts/{id}` з `desiredSalePrice` |
| Маржа                                                      | `(ціна − собівартість) / ціна`, кольори як у макеті: ≥30% зелений, >0 бурштиновий, ≤0 червоний  |
| «Зберегти й додати ще»                                     | форма лишається відкритою, поля скидаються, лічильник позицій приймання зростає                 |
| «Додані щойно»                                             | список того, що додано в цьому сеансі, з коміркою й кількістю                                   |

### Чого застосунок не вміє

1. **OEM-код.** Поле є в макеті, але його немає ні в `AddPartToIntakeRequest`,
   ні в `UpdatePartRequest`. Зараз поле показане неактивним із підказкою, що
   код вписують на картці деталі. **Треба бекенд:** `oemCode` у запиті
   додавання деталі в приймання (він уже є в самій сутності `Part`).
2. **Собівартість у гривнях.** Макет показує `127,5 $` і `5 228 ₴` з курсом
   41, зашитим у канву. У системі немає ні курсу, ні поля валюти приймання —
   показую лише долари. **Треба рішення:** звідки брати курс (ручне поле в
   налаштуваннях розбірки чи довідник НБУ) і чи потрібна гривня взагалі.
3. **Сканувати комірку.** Кнопка є, камера до форми не підключена — у нас
   сканер живе окремим екраном `/scan`. Кнопка неактивна з поясненням.
   **Треба фронт:** зчитування QR комірки без виходу з форми.
4. **Підказані комірки** (`A-01-04`, `A-01-05` …). У макеті це чотири
   зашиті значення. Замінив на справжній список зон із сервера — фільтра
   «найближчі до цього приймання» немає, бо приймання не привʼязане до зони.
5. **Контекст приймання в шапці** — макет показує «Ангар · зона». Приймання
   в нас не має ні складу, ні зони, тому лишив назву приймання й кількість
   позицій. **Треба бекенд:** привʼязка приймання до складу, якщо це потрібно.

## 2. Редагування запчастини — `/parts/:partId/edit`

Артефакт: `470f2d21-83e7-4980-a0fd-6d12cf056999`
Реалізовано: так, UI за макетом.

### Працює по-справжньому

| Елемент макета                                                       | Як зроблено                                                                                             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Липка шапка з «Скасувати» / «Зберегти зміни»                         | кнопка в шапці сабмітить форму через `form="part-edit"`                                                 |
| Картка «Джерело», лише для читання, з переходом на авто чи приймання | `PartDetail.carId / carCode / intakeId`; посилання під правами на модуль                                |
| «Опис деталі»: назва, тип, стан чипами, нотатки                      | `PUT /parts/{id}`                                                                                       |
| «Кількість і ціна»: кількість кроками, одиниця, бажана ціна          | той самий запит, ціна через `desiredSalePrice`                                                          |
| «Сумісність» лише для читання                                        | `compatCarBrand / compatCarModel / compatCarYear` у сітці `SpecGrid`                                    |
| Фото                                                                 | наявний завантажувач із чергою й повторами                                                              |
| «Зведення»: доступно, у резерві, QR-код                              | з деталі                                                                                                |
| «Надрукувати стікер»                                                 | веде на `/stickers?part=<id>`; екран стікерів тепер приймає цей параметр і ставить деталь у чергу друку |
| «Видалити запчастину» з поясненням                                   | `DELETE /parts/{id}`; текст залежить від того, чи є резерв                                              |

### Чого застосунок не вміє

1. **OEM-код** — те саме, що й у макеті №1: поля немає в `UpdatePartRequest`,
   тож воно показане неактивним. **Треба бекенд.**
2. **«Зона B · B-04-12» у підзаголовку.** Розміщення деталі лежить в окремому
   модулі (`/parts/{id}/inventory`), у `PartDetail` його немає. Показую QR-код
   і автора створення. **Треба бекенд:** поточна зона в `PartDetailDto`.
3. **«Змінено 15.09.2026 · Олена».** У деталі є лише `createdAt` і
   `createdByName`; хто і коли змінював востаннє — невідомо.
   **Треба бекенд:** `updatedAt` + `updatedByName`.

## 3. Результат сканування — `/scan` (і `/scan/:qrCode`)

Артефакт: `a022b812-ea11-4c25-b577-289a8faf638e`
Реалізовано: так, перебудовано область результату.

### Працює по-справжньому

| Елемент макета                                                  | Як зроблено                                                            |
| --------------------------------------------------------------- | ---------------------------------------------------------------------- |
| «Код розпізнано» з назвою, статусом і залишком                  | `GET /parts/qr/{code}` віддає повну картку деталі                      |
| Стан деталі поруч зі статусом                                   | `condition` з тієї ж відповіді                                         |
| «Що зробити» → «Розміщення» з поточною коміркою і «Перемістити» | `GET /parts/{id}/inventory-zones`, перехід на `/parts/{id}/inventory`  |
| «Стікер» → «Надрукувати»                                        | `/stickers?part=<id>` — та сама черга друку, що й з редагування деталі |
| «Джерело» з переходом на авто                                   | `carId` / `carCode` з відповіді                                        |
| «Рух запчастини» з переходом на повну історію                   | `GET /parts/{id}/history`, показані три останні події                  |
| «Попередні скани коду»                                          | памʼять сеансу: пʼять останніх кодів цього пристрою                    |

### Чого застосунок не вміє

1. **«Центральний · зона B · ходова, підвіска»** — макет показує склад, зону й
   призначення комірки одним рядком. `GET /parts/{id}/inventory-zones` віддає
   зону, але не склад і не її опис. **Треба бекенд:** склад і опис у відповіді
   про розміщення деталі.
2. **Назви подій історії** тут показані як є (`created`, `reserved`), бо
   словник людських назв живе на екрані деталі. Варто винести його в спільне
   місце — це вже наша робота, не бекенду.

## 4. Редагування приймання — `/intakes/:intakeId/edit` (і `/intakes/new`)

Артефакт: `dd3df589-0b83-47e4-8ea0-e85252933b06`
Реалізовано: так, форму приймання перебудовано за макетом.

### Працює по-справжньому

| Елемент макета                                  | Як зроблено                                                                               |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Липка шапка: «Скасувати» / «Зберегти зміни»     | кнопка в шапці сабмітить форму через `form="intake-form"`                                 |
| Хлібні крихти «Склад · Приймання · назва»       | назва партії з `GET /intakes/{id}`                                                        |
| Підзаголовок «6 позицій · 48 шт»                | `partsCount` і сума `quantity` по позиціях приймання                                      |
| Картка 01 «Джерело надходження» з замком        | на редагуванні джерело справді не змінюється; «Постачальник» і «Назва» пишуться в `PATCH` |
| Картка 03 «Дата приймання»                      | `purchasedAt`, поле `type="date"`; незмінене значення йде на сервер таким, як прийшло     |
| Картка 03 «Відповідальний»                      | `createdBy` з ініціалами — хто прийняв партію                                             |
| Картка 04 «Загальна вартість»                   | `totalCost`, лише з `finance.manage`; помилка валідації як була                           |
| Підказка «Сума ділиться між позиціями»          | так і рахується собівартість позиції у формі додавання деталі                             |
| Картка 04 «Коментар»                            | `notes`                                                                                   |
| Фото партії (лише створення)                    | `photoKeys` у `POST /intakes`                                                             |
| Зведення: постачальник, дата, кількість позицій | з тієї ж відповіді й полів форми                                                          |
| Зведення: «Сума придбання» / «Разом»            | з поля вартості, у доларах                                                                |
| Чеклист унизу зведення                          | три справжні перевірки: назва, постачальник, сума                                         |
| «Скасувати приймання»                           | `DELETE /intakes/{id}` з тим самим підтвердженням, що й на картці приймання               |

### Чого застосунок не вміє

1. **Вид джерела (з авто / від постачальника / з аукціону).** У макеті це три
   картки, від яких залежить і підказка про собівартість, і те, що питають далі
   (авто, постачальник, лот). У нас приймання має лише вільний текст
   `supplier` — виду джерела немає ні в `CreateIntakeRequest`, ні в
   `UpdateIntakeRequest`, ні в `Intake`. Картки показані неактивними з
   поясненням. **Треба бекенд:** `sourceKind` + звʼязок із авто чи лотом.
2. **Склад і зона приймання.** Картка 02 «Куди приймаємо» в макеті задає
   розміщення за замовчуванням для всіх позицій партії. У прийманні таких полів
   немає — розміщення живе тільки на деталі (`/parts/{id}/inventory`). Показую
   справжні склади й зони з сервера, але неактивними. **Треба бекенд:**
   `warehouseId` / `zoneId` у прийманні.
3. **Документ постачальника.** Поле є в макеті (номер накладної), у запитах
   приймання його немає. Показане неактивним; найближче, що в нас є, — назва
   партії. **Треба бекенд:** `documentNumber`.
4. **Супутні витрати.** Макет рахує «Разом = сума придбання + витрати» й окремим
   рядком показує витрати у зведенні. У нас одна сума `totalCost`, тож рядок
   «Витрати» показано прочерком. **Треба бекенд:** `additionalCost`, і разом із
   ним — перерахунок собівартості позицій.
5. **Відповідальний як окрема особа.** Макет дає вибір із трьох працівників. У
   нас є лише `createdBy` — хто створив приймання; змінити відповідального
   нікуди. **Треба бекенд:** `responsibleUserId` у прийманні.
6. **«Змінено 15.09.2026, 16:20 · Андрій».** Те саме, що й на картці деталі:
   `updatedAt` / `updatedByName` немає. Показую «Створено … · автор».
7. **«15 одиниць партії ще не розміщені».** Скільки одиниць партії лежить без
   комірки, ми не знаємо — розміщення рахується по деталях. Замість цього
   показую кількість позицій. **Треба бекенд:** лічильник нерозміщених одиниць
   у прийманні.
8. **«Скасувати приймання» — це видалення.** У нас `DELETE /intakes/{id}`
   видаляє приймання, а не «повертає позиції зі складу», тож кнопка названа
   чесно: «Видалити приймання». Статусу «скасоване» приймання не має.

## 5. Картка приймання — `/intakes/:intakeId`

Артефакт: `c6574dac-8f86-4789-87e8-47aebb2c9869`
Реалізовано: так, екран перебудовано за макетом.

### Працює по-справжньому

| Елемент макета                                      | Як зроблено                                                                                       |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Липка шапка з «Редагувати», «Додати деталь» і «···» | ті самі дії під тими самими правами; «···» розгортає рядок додаткових дій, як у макеті            |
| Статус-пігулка біля назви                           | рахується з `soldCount` / `partsCount`: нічого не продано · розпродається · розпродано            |
| Підзаголовок: постачальник, дата, автор             | `supplier`, `purchasedAt`, `createdBy` з `GET /intakes/{id}`                                      |
| Смуга показників                                    | позицій і одиниць — із `parts`; продано — `soldCount`; гроші — `profitability` під `finance.view` |
| «Позиції приймання» з перемикачем і лічильниками    | справжні позиції приймання; фільтри «Усі / Доступні / Продані» рахуються з `status` позицій       |
| Колонка «Код»                                       | `qrCode` позиції                                                                                  |
| Колонка «Собів.»                                    | `totalCost / partsCount` — та сама арифметика, що й у формі додавання деталі                      |
| Колонка-пігулка праворуч                            | `status` позиції (доступна · у резерві · продана)                                                 |
| «Історія»                                           | будується з міток часу, які справді є: коли приймання створено і коли додано кожну позицію        |
| Картка «Собівартість» у правій колонці              | `totalCost`, на позицію, повернено — з `profitability`                                            |
| Картка «Продаж партії» зі смугою                    | `soldCount` проти `partsCount`, під смугою — доступно/продано з `profitability`                   |
| «Друк стікерів партії»                              | веде на `/stickers?part=…&part=…`; екран стікерів тепер приймає кілька позицій одразу             |
| «Скасувати приймання»                               | `DELETE /intakes/{id}` з тим самим підтвердженням                                                 |
| Нотатки й фото партії                               | `notes` і `photos` — у макеті їх немає, але це справжні дані, тому лишив окремими картками        |

### Чого застосунок не вміє

1. **Розміщення партії.** Макет має і колонку «Розміщення» з коміркою кожної
   позиції, і картку «33 з 48 шт · 15 очікують комірку» з кнопкою «Розмістити
   решту». `GET /intakes/{id}` не віддає розміщення позицій, а рахувати його
   запитом на кожну деталь — це N запитів на екран. Замість цього показую стан
   позиції та прогрес продажу. **Треба бекенд:** зона в `IntakePartDto` і
   лічильник нерозміщених одиниць у прийманні.
2. **Ціна позиції.** Макет показує колонку «Ціна» поруч із собівартістю.
   `IntakePartDto` несе `quantity`, `unit`, `status`, але не `desiredSalePrice`,
   тож колонки немає. **Треба бекенд:** бажана ціна в позиціях приймання (або
   «потенціал продажу» одним числом на приймання — макет показує і його).
3. **OEM-код під назвою позиції.** Те саме, що й на макетах №1 і №2: у
   `IntakePartDto` немає `oemCode`. Показую тип деталі.
4. **Справжня історія приймання.** Макет показує події «розміщено 12 одиниць»,
   «собівартість розподілено» з автором і часом. У нас такого журналу немає —
   є лише `createdAt` самих записів. **Треба бекенд:** `GET /intakes/{id}/history`
   на кшталт того, що вже є для деталей.
5. **Номер приймання (IN-0310) і «накладна №4471».** Приймання не має ні
   людського коду, ні номера документа — у шапці показую назву партії.
6. **Постачальник як сутність.** Макет дає перехід на картку постачальника з
   «12 приймань · 486 позицій». У нас `supplier` — вільний текст, тож картка
   нікуди не веде й лічильників не має. **Треба бекенд:** довідник
   постачальників.
7. **«Додати партією».** Масового додавання позицій немає — кнопка неактивна з
   поясненням; деталі додаються по одній через `POST /intakes/{id}/parts`.

## 6. Приймання партією — `/intakes/:intakeId/parts/batch`

Артефакт: `d1acffbc-5a0a-48ff-ba87-c6f8b70ac25b`
Реалізовано: так, новий екран.

### Працює по-справжньому

| Елемент макета                                        | Як зроблено                                                                                           |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Таблиця рядків із назвою, кількістю, ціною й коміркою | кожен заповнений рядок іде окремим `POST /intakes/{id}/parts`, ціна — `PUT /parts/{id}`               |
| «Додати рядок» / «×»                                  | рядки живуть у стані форми; порожні не зберігаються                                                   |
| «Заповнити комірку вниз»                              | бере комірку з першого рядка, де вона є, і ставить її всім заповненим рядкам без власної              |
| «Спільні властивості»: стан і комірка                 | стан іде в `condition` кожної позиції, комірка — у `inventoryZoneIds`, якщо в рядка своєї немає       |
| Зведення «Партія»                                     | позицій, одиниць, сума за цінами; собівартість партії з `totalCost`, на позицію — з урахуванням нових |
| «Перевірка»                                           | три справжні перевірки: готові позиції, позиції без комірки, позиції без ціни                         |
| Кнопка «Прийняти N позицій»                           | шле рядки по черзі й показує, скільки вже прийнято                                                    |
| Помилка посеред партії                                | прийняті позиції лишаються на сервері, неприйняті — у таблиці, з поясненням, де все зупинилося        |

### Чого застосунок не вміє

1. **Одного запиту на всю партію немає.** `POST /intakes/{id}/parts` приймає одну
   позицію, тож екран шле N запитів підряд. Для 6–10 позицій це нормально, для

### Чого застосунок не вміє

1. **«Змінено 14.09.2026, 11:02 · Дмитро».** `Car` несе тільки `createdAt` —
   підпис показує дату створення. **Треба бекенд:** `updatedAt` / `updatedBy`.
2. **Декодування VIN і OEM.** Ручки декодування немає — марку, модель і рік
   заповнюємо вручну; підказка під полем каже це прямо.
3. **Фото при редагуванні.** `UpdateCarRequest` не приймає `photoKeys`, тож на
   збереженому авто фото показані, але не змінюються. **Треба бекенд:** зміна
   фото авто.
4. **Витрати при редагуванні.** Форма редагування не змінює витрати — вони
   живуть на картці авто, де є повний набір дій; секція показує їх і веде туди.
5. **Умова видалення.** Чи можна видалити авто, вирішує сервер; кнопка є, а
   відмову показуємо текстом помилки.
