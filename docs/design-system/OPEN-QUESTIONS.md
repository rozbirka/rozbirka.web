## Модуль 46 · Нова пошта (§1–3, web)
- D18. 2.2: у макеті редагування немає поля ключа, але Core змінює відправника, контакт і точку лише через сеанс підключення, а сеанс починається з ключа (збережений ключ Core не повертає). Поле «API-ключ» з’являється тільки коли змінено відправника, контакт або точку, з підказкою «Нового відправника, контакт чи точку Нова пошта перевіряє лише з ключем. Збережений ключ ми не показуємо — вставте його ще раз.» Зміна лише каси йде без ключа (`PUT shipping/preferences`).
- D19. 2.2: «Точка відправлення» в режимі редагування — вибір серед активних точок відправлення інтеграції (Core після збереження робить її єдиною типовою «Основна»).
- D20. 2.3: кількість чернеток у підсумку («у 2 відкритих замовленнях») Core не повертає — рядок без числа: «Чернетки доставки у відкритих замовленнях треба буде перевірити перед створенням ТТН.» Рядок «… не змінюються» складається з назв незмінених полів. Для зміни лише каси опис — «Зміни діятимуть для нових накладних.» (у Новій пошті нічого не перевіряється).
- D21. 2.8: Core не каже, хто й коли змінив налаштування (`np_configuration_changed`), тож замість «змінив Олег К. (19:42)» — «змінив інший користувач».
- D22. 1.18: «Вийти» не скасовує сеанс — перевірений ключ живе в сеансі Core до `expiresAt` (1 год), id сеансу зберігається в браузері; наступний вхід у майстер протягом цього часу починається з кроку 2. Після спливу сеансу — знову крок 1 з поясненням.
- D23. 3.3: дат «за 08–09.2026» і списку всіх накладних кабінету Core не дає (`connections` має лише `waybillCount`) — шторка показує відомі виклику накладні (із замовлення — одну) і «І ще N накладних.» без дат.
- D24. 3.5: `recover` відновлює доступ одразу після успішної перевірки; «Застосувати» лише закриває шторку й показує тост 3.9. Закриття шторки після успіху теж вважається застосуванням.
- D25. 3.6: Core не відрізняє «ключ поточного кабінету» від іншого непідтвердженого ключа (`np_historical_scope_unverified`), тож обидва випадки показуються як 3.7.
- D26. 3.2: «Відкрити ТТН» відкриває картку ТТН (розділ 8, `/sales/waybills/:id`). Стан «Немає доступу» в замовленні й на картці видно лише з правом «Налаштування інтеграцій» — без нього Core не віддає список кабінетів.

## Модуль 46 · Нова пошта (§4–6, web)
- D27. 4.2: у формі «Посилка» — «Місць», загальна «Вага» й одні «Габарити». Core зберігає місця окремо, тож N місць записуються як N однакових місць із вагою, поділеною порівну. Поле «Погоджено за доставку, UAH» з’являється в групі «Післяплата» лише коли Core ще не знає погодженої суми замовлення (`agreedTotalUah = 0`) — інакше залишок і післяплату нема з чого порахувати.
- D28. 4.10: причину відмови Нова пошта віддає лише вільним текстом у повідомленні Core, якого кабінет не показує. Текст без причини: «Нова пошта відхилила накладну. Дані збережено — змініть відділення або габарити й спробуйте ще раз.»

Блок показує текст макета, а «Створити ТТН» у підтвердженні вимкнено з підказкою «Спершу внесіть депозит за доставку.» ? Яке правило вірне — створювати ТТН до депозиту чи ні?
- D30. 2.9: старої суми розрахунку Core після зміни налаштувань не зберігає, тож «Вартість доставки» — «— · розрахунок застарів» без «було 128 ₴». Стан визначається так: точка відправлення чернетки більше не активна. «Перевірити й розрахувати» відкриває форму з новою точкою, після збереження — перевірку й розрахунок.
- D31. 5.14: Core не шукає кандидата сам (`reconcile` без номера → `shipment_candidate_required`), тож шторка просить ввести номер із кабінету НП і показує, з чим його звірити (отримувач, маршрут, післяплата замовлення). Опис: «Створення ТТН для замовлення #N не підтверджено. Знайдіть накладну в кабінеті Нової пошти й введіть її номер.» Успіх — лише коли Core підтвердив номер замовлення, відправника й післяплату.
- D32. 5.15: часу автоматичної перевірки Core не повідомляє — речення «Перевіримо автоматично о 20:15» прибрано. Для невідомого скасування — той самий текст із «чи скасовано накладну».
- D33. 5.x: «Редагувати» й «Скасувати ТТН» є на картці ТТН (8.2) і залишаються в блоці доставки замовлення для створеної, ще не відправленої ТТН (карта екранів: «Картка / блок ТТН»). 5.6 у замовленні — блок скасованої ТТН з «Залишився один крок» і «Створити нову ТТН». Core da5ba24 на будь-яке редагування відповідає `shipment_not_editable` або `shipment_recreate_required`, тож на практиці зміна завжди йде через нову ТТН (діалог «Потрібна нова ТТН», текст «Нова пошта не змінює ці дані в чинній накладній — потрібна нова ТТН.»).
- D34. 5.8: Core після скасування більше не повертає ТТН для замовлення, тож блок «ТТН скасована» з номером видно до перезавантаження сторінки; після нього — стан 4.1.
- D35. 6.1: Core звіряє зовнішню ТТН з отримувачем і точкою відправлення чернетки, тож без чернетки шторка пояснює «Спершу оформіть доставку: …» і пропонує «Оформити доставку». Кнопку «Прив’язати накладну з кабінету НП» додано й у блок чернетки (4.4).
- D36. 6.7: Core не відрізняє «накладна іншого кабінету» від «не знайдено» (обидва 404), тож показується 6.6. 6.10: номера іншого замовлення Core не повертає — «Ця ТТН уже прив’язана до іншого замовлення. Одна накладна — одне замовлення.» 6.5/6.11: дати отримання в попередньому перегляді немає — «Отримано» без дати. 6.4: назви статусу НП у попередньому перегляді немає (лише код) — «Відправлено».
